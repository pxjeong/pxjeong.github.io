게시판에서 검색창에 공지사항을 입력하고 검색 버튼을 누르면 브라우저는 웹 서버에 해당 단어가 들어간 글을 찾아 달라고 요청한다. 여기서 요청은 브라우저가 서버에 어떤 작업을 해 달라고 보내는 메시지다. 서버는 요청에 따라 게시글을 찾고, 결과를 브라우저로 돌려준다.

 

그런데 게시판을 이용하는 사람 모두가 글을 검색하러 들어오는 것은 아니다. 누군가 다른 사람의 계정에 들어가려고 여러 차례 로그인을 시도할 수도 있다. 이렇게 허락받지 않은 방식으로 계정이나 시스템에 접근하는 행위가 침입의 한 예시라고 볼 수 있다. 이때 여러 번의 로그인 실패는 침입을 의심할 만한 신호가 될 수 있다. 실제 사용자가 비밀번호를 여러 번 틀렸을 수도 있어서 그 신호만으로 침입이 일어났다고 단정하기는 어렵다.

 

이런 의심스러운 활동을 발견하거나 막기 위해 사용하는 시스템이 IDS와 IPS다.

 

 

 

IDS와 IPS는 무슨 일을 할까?

 

 

IDS는 Intrusion Detection System의 약자로 우리말로는 침입 탐지 시스템이다. 여기서 탐지는 의심스러운 활동을 발견한다는 뜻이다. IDS는 시스템에서 일어나는 활동을 살펴보다가 의심스러운 흔적을 발견하면 경보를 남긴다. 운영자는 이 경보를 보고 어떤 일이 있었는지 확인할 수 있다.

 

IPS는 Intrusion Prevention System의 약자로 우리말로 침입 방지 시스템이다. IPS도 의심스러운 활동을 찾아낸다. 여기에 차단 기능이 있기에 미리 정해 둔 차단 조건에 해당하면 해당 통신을 막을 수 있다. IPS에서도 어떤 조건에는 경보만 남기고 다른 조건에는 차단까지 하도록 설정할 수 있다.

 

그렇다면 같은 웹 요청을 발견했는데 왜 한쪽은 경보를 남기고 다른 쪽은 서버에 도착하기 전에 막을 수 있을까? 네트워크에서 두 시스템이 데이터를 어떻게 받아 보는지 살펴보면 이해하기 쉽다.

 

 

 

같은 웹 요청을 IDS와 IPS는 어디에서 살펴볼까?

앞서 나온 내용에선 브라우저가 웹 서버에 요청을 보낸다 했는데 브라우저와 서버 사이에서 데이터가 오가는 통신망을 네트워크라고 그 안에서 데이터를 보내는 작은 단위를 패킷이라고 부른다. 웹 요청 하나도 여러 패킷에 걸쳐서 전달 될 수 있다. 이제 이 패킷이 서버까지 가는길을 따라가보자

 

  • IDS에 패킷의 복사본을 보내는 경우
    • 원본 패킷은 웹 서버로 향하고 IDS는 옆에서 그 복사본을 받아 검사한다. IDS가 복사본에서 의심스러운 내용을 발견하면 경보를 남긴다. 원본은 별도의 경로로 계속 이동하므로 웹 서버는 요청을 받아 응답할 수 있다. 이렇게 실제 통신이 지나가는 길 옆에서 복사본을 관찰하는 방식을 수동 감시 방식이라고 한다.
  • IPS를 패킷이 지나가는 길에 두는 경우
    • 웹 서버로 향하는 패킷이 IPS를 거쳐 간다. IPS는 패킷을 검사하고 통과시킬 패킷은 서버 쪽으로 보낸다. 차단 조건에 해당하는 패킷은 버릴 수 있다. 이렇게 실제 데이터가 지나가는 경로 중간에 장비를 두는 방식을 인라인(inline) 배치라고 한다.

뭔가 말이 어려워 보일 수 있어서 예를 들어보자. 게시판 검색창에 ids-demo 라는 테스트 문구를 입력해본다고 치자.

두 시스템이 문구를 찾도록 설정 했다고 가정을 해보자. 복사본을 보는 IDS는 문구를 발견하고 경보를 남긴다. 하지만 경고만 남길뿐 원본은 계속 이동을 하므로 웹서버에 요청을 보낸다. IPS는 인라인 IPS에서 차단 규칙을 설정 했다면 IPS는 문구가 들어 있는 패킷을 발견 했을때 서버로 보내지 않는다. 같은 문구를 발견해도 실제로 서버로 가는 데이터를 처리 할 수 있는 위치인지, 그리고 차단하도록 설정 했는지에 따라서 결과가 달라진다.

 

같은 테스트 요청을 보냈을 때 수동 감시 방식의 IDS 인라인 IPS에 차단 규칙을 설정한 경우
장비가 검사하는 데이터 패킷의 복사본 서버로 가는 실제 패킷
테스트 문구를 발견한 뒤 경보를 남긴다. 일치한 패킷을 버리고 경보를 남길 수 있다.
웹 서버에서 일어나는 일 요청을 받아 검색 결과를 돌려줄 수 있다. 차단된 패킷이 도착하지 않아 해당 요청을 정상적으로 처리할 수 없다.

 

 

여기까지는 네트워크에서 자주 쓰이는 두 가지 배치를 비교한 것이다. 뒤에서 살펴볼 호스트 기반 시스템은 서버나 PC 내부에서 일어나는 일을 관찰해보자

 

 

 

무엇을 보고 의심스럽다고 판단할까?

앞의 예시에선 dis-demo라는 문구를 미리 정했다. 실제 환경에선 이렇게 이미 알고 있는 특징을 찾기도 하고 평소와 다른 행동이나 통신 순서에서 벗어난 동작을 찾아내기도 한다.

 

시그니처 기반 탐지

시그니처는 시스템이 찾아낼 수 있도록 미리 등록해 둔 특징이나 패턴이다. 요청에서 특정 문자열이 나타나는지를 조건으로 정했다면 시스템은 그 조건과 일치하는지 확인한다. 앞에서 ids-demo를 찾은 방식이 여기에 해당한다.

이 방식은 경보가 어떤 조건에 걸려서 발생했는지 확인하기 쉽다. 알고 있는 패턴을 찾는 데 유용하고 등록된 규칙이 다루지 않는 패턴은 놓칠 수 있다.

 

이상 탐지

이상 탐지는 평소와 비교해서 얼마나 달라졌는지를 살펴본다. 예를 들어 평소 새벽에는 외부로 보내는 데이터가 거의 없던 서버가 어느 날 새벽에 갑자기 대량의 데이터를 전송하면 시스템이 이 변화를 감지할 수 있다.

알려진 공격 패턴이 없어도 평소와 다른 행동을 발견할 수 있다. 다만 그날부터 새벽에 정기 백업이 시작됐다면 정상적인 변경에도 경보가 울릴 수 있다.

 

상태 기반 프로토콜 분석

프로토콜은 컴퓨터끼리 데이터를 주고받을 때 따르는 약속이다. 상태는 그 통신이 현재 어느 단계에 있는지를 뜻한다.

예를 들어 파일을 주고받는 통신 규칙인 FTP에서 로그인을 마친 뒤에만 할 수 있는 작업이 있다고 하자. 시스템은 로그인 전인지 후인지 추적하고 그 단계에서 허용되는 순서대로 동작하는지 검사할 수 있다. 반대로 누군가 통신 순서를 모두 지키면서 악의적인 행동을 한다면 순서를 검사하는 것만으로는 그 의도를 알아차리기 어렵다.

 

 

 

어디를 살펴보느냐에 따라 유형도 달라진다

 

웹 서버 앞에서 패킷을 살펴볼 수도 있고, 서버 안에서 중요한 파일이 바뀌었는지 확인할 수도 있다. 어떤 정보를 어디에서 관찰하느냐를 기준으로 보면 다음과 같이 나뉜다. 여기서 호스트는 네트워크에 연결된 개별 서버나 PC를 뜻한다.

 

 

유형 무엇을 살펴보나? 예시
네트워크 기반 장비가 설치된 지점을 지나는 데이터 웹 서버로 향하는 요청에서 등록된 패턴이 발견되는지 확인한다.
호스트 기반 개별 서버나 PC의 로그, 실행 중인 프로그램, 파일 변경 서버의 중요한 설정 파일이 변경됐는지 확인한다.
무선 기반 Wi-Fi 통신과 주변 무선 장비 회사에서 허가한 목록에 없는 무선 공유기가 감지됐는지 확인한다.
네트워크 행위 분석(NBA) 누가 누구와 통신했는지, 연결이 몇 번 발생했는지, 얼마나 많은 데이터를 보냈는지 서버 한 대가 평소보다 훨씬 많은 목적지로 연결을 시도했는지 살펴본다.

 

 

예를 들어 웹 서버 앞에 놓인 장비가 요청의 특정 문자열을 찾는다면 관찰 대상은 네트워크 트래픽이고 판단 방식은 시그니처 기반 탐지다. 장비가 실제 통신 경로에서 일치한 패킷을 차단한다면 인라인 IPS로 동작하는 사례가 된다.

 

 

더보기

TMI : 내가 이전 블로그에서 썼었던 Wazuh는 호스트 기반 침입 탐지 시스템으로 능동 대응(Active Response) 기능을 통해 IPS와 유사한 차단 역할도 수행할 수 있다.  탐지 기능과 차단 역할도 공격 룰 규칙과 스크립트를 넣으면 되므로 IPS에 가깝다. 하지만 또 탐지 후 호스트/방화벽 수준에서 대응하는 형태이므로 IPS라고 단정은 못짓는다.

현재 Wazuh는 단순 IDS/IPS를 넘어 로그 수집 및 분석(SIEM), 위협 탐지 및 대응(XDR) 기능을 아우르는 오픈소스 보안 플랫폼으로 쓰인다.

 

실제로 활용할 때는 무엇을 고려해야 할까?

 

정상적인 활동도 차단될 수 있다

 

앞에서 새벽 정기 백업을 의심스러운 전송으로 판단하는 예시가 나왔다. 이렇게 정상적인 활동을 위협으로 잘못 판단하는 것을 오탐(False Positive)이라고 한다. 수동 감시 방식의 IDS라면 운영자가 확인해야 할 경보가 하나 늘어난다. 같은 판단에 IPS 차단까지 걸려 있으면 정상 백업이 중단될 수 있다.

반대로 실제 위협을 발견하지 못하는 것을 미탐(False Negative)이라고 한다. 예를 들어 서버에서 허가받지 않은 데이터 전송이 일어났는데 경보가 없었다면 미탐이다. 차단 규칙을 적용하기 전에 경보 기록을 살펴보면 해당 규칙이 평소 어떤 정상 활동에도 반응하는지 확인할 수 있다. 이때 언제 경보가 발생했는지 어느 장비에서 어느 장비로 통신했는지, 어떤 규칙에 걸렸는지를 함께 본다.

 

 

실제 통신 경로에 장비를 두면 성능도 살펴봐야 한다

수동 감시 방식에서는 원본이 장비를 거치지 않아서 장비가 복사본을 검사하는 동안에도 원본은 서버로 이동한다. 그만큼 운영 중인 통신에 직접 영향을 주지 않고 경보를 모으기 좋다. 경보를 발견한 뒤 조사하고 대응하는 과정은 별도로 필요하다.

인라인 IPS는 검사와 차단을 통신 도중에 할 수 있다. 그만큼 장비의 처리 속도도 중요해진다. 트래픽이 많을 때 장비가 제때 검사하지 못하면 정상적인 요청도 느려질 수 있다.

 

 

참고! HTTPS를 쓰면 요청 내용이 암호화된다

HTTPS를 사용하면 브라우저와 웹 서버 사이에서 검색어 같은 요청 내용이 암호화된다. 암호화는 통신 도중 데이터를 보더라도 원래 내용을 바로 읽을 수 없게 바꾸는 과정이다.

앞의 ids-demo 예시를 떠올려 보자. Suricata가 암호화된 구간만 보고 있다면, 누가 어느 서버와 통신하는지 같은 일부 정보는 확인할 수 있어도 검색 요청에 ids-demo가 들어 있는지는 읽을 수 없다. 그래서 웹 요청의 내용까지 확인해야 한다면 암호가 풀리는 지점에서 검사할 수 있는지, 또는 서버가 남긴 기록에서 필요한 정보를 확인할 수 있는지도 함께 봐야 한다.

 

 

 

 

마무리

처음에는 IDS는 탐지, IPS는 차단이라고 외우면 된다고 생각했다. 같은 웹 요청이 지나가는 길을 따라가 보니 차단하려면 장비가 실제 통신에 개입할 수 있는 위치에 있어야 하고 차단할 조건도 정해져 있어야 한다는 점이 더 잘 이해됐다. 로그인 실패나 통신량 증가처럼 정상 상황에서도 생길 수 있는 신호를 보고 있으면 경보의 근거를 확인한 뒤 어떤 조건에 차단까지 적용할지 정하는 과정이 중요하다고 생각한다. 오늘 한 공부 덕분에 네트워크에 대해서 좀 더 잘 아는 시간이 됐다!

참고자료

  • Cisco, Managing IPS Device Interface — 장비가 패킷의 복사본을 받는 방식과 실제 통신 경로에 설치되는 방식의 차이를 설명한다. Cisco 공식 문서
  • Suricata User Guide, IPS Concept / Rules Format — 인라인 IPS가 트래픽을 어떻게 처리하는지, 규칙에서 경보와 차단을 어떻게 구분하는지 확인할 수 있다. IPS Concept · Rules Format
  • Suricata User Guide, EVE JSON Format / Encrypted traffic — 경보 기록에 어떤 항목이 남고, 암호화된 트래픽을 어디까지 관찰할 수 있는지 설명한다. EVE JSON Format · Encrypted traffic
